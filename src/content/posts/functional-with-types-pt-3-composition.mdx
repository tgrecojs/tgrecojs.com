## The question

In the [currying post](/posts/functional-with-types-pt-2-curried-functions), we learned how to decouple transformer logic from the data that it operates on. In this post, i'll build on concepts discussed in that post to bring function composition into the fold. By the end, we'll learn the ins-and-outs of function composition starting from the theory behind it, along the way learning how use of functional composition makes our software mathematically provable, and why that is useful. I'll be threading in TypeScript types throughout the way too to see how we can create incredibly generic functions that are strongly typed.

Our north star for this post is the following `compose` and `pipe` functions.

```typescript
// need to type these
const compose =
  (...fns) =>
  (initialValue) =>
    fns.reduceRight((acc, fn) => fn(acc), initialValue);
const pipe =
  (...fns) =>
  (initialValue) =>
    fns.reduce((acc, fn) => fn(acc), initialValue);
```

get the most out of our functions - applying them as need be. up a whole chain of transformations before the data arrives. Each function passes its result to the next.

Say we want to check whether a post summary fits within its character limit. We trim the text, count its characters, and compare that count with the limit. If we count first and then try to trim the result, we’re handing a number to a function that expects a string. Can TypeScript catch that when we put the functions together?

We’ll start with two functions to see how their types fit together. Then we’ll extend the same idea to a pipeline that accepts a variable number of functions, checks each connection, and infers the type of the function it returns.

Can the compiler check every connection between transformations and infer the function produced by their composition?

## f of g of x

Nearly ten years ago is when I had a fairly major a-ha moment after seeing the overlap between deterministic software, and basic algebra. At the heart of this epiphany was the laws of function composition.

$$
(f \circ g)(x) = f(g(x))
$$

Given an input `x` and functions `f` and `g`, `(f ∘ g)(x)` is always equal to `f(g(x))`. It's important to note that this definition holds for any function. What **pure functions** give us is the guarantee that `f(g(x))` returns the same answer every time we call it. That guarantee is what lets us treat our code like an algebra problem.

> Pure functions are functions that given an input, always return the same output, rely on no external state, and mutate no external state.

Before we dive into function composition, let's quickly get a firm grasp on pure functions. Below, we have 2 approaches for adding `10` to a value. The first code block is **impure**. It relies on shared state. If someone were to mutate `tenValue` to be `20`, then we can no longer rely on `addTen` to produce the correct output.

```ts
let tenValue = 10;

const addTen = (x: number) => x + tenValue;

addTen(10); // 20
tenValue = 20;
addTen(10); // 30
```

One of the ways in which we can circumvent the need for relying on global state is through currying. Below, we're achieving the result of creating a function that adds `10` to a value without opening our software up to the possibility that someone may change (or _mutate_) a value that results in our `addTen` function producing an incorrect output.

```ts
const add = (x: number) => (y: number) => x + y;
const addTen = add(10);

addTen(10); // 20
```

Because pure functions abide by these rules, we can combine them together to create chains of functions. Let's say we have a classic `greeter` function that takes in a string and then appends that value to the string `Hello`.

```
let greeting = `Hello`
const greeter = (name) => `$${greeting}, {name}`;

greeting = `I really do not care for you,`
greeter('friend.') // I really do not care for you, friend... not nice
```

> Outline note: `greeter` is the counterexample for substitution, which pays off in "Why we can trust the chain." Before `greeting` changes, `greeter('friend.')` can be replaced with its result. After it changes, the same call returns something else, so it can't. The template also needs fixing: as written it prints `$Hello, {name}`; it should be `` `${greeting}, ${name}` ``.

## Start with the runtime order

For pipe(f, g), evaluate g(f(value)). For compose(g, f), evaluate the same expression. Use unequal input/output types so swapping the order produces a visible mistake. State that these helpers build a function; some libraries call this form flow and reserve pipe for a value-first API.

Show order with the north star `pipe` and two number functions, `addTen` and `double`: `pipe(addTen, double)(1)` is `22`, and `pipe(double, addTen)(1)` is `12`. Same functions, different order, different answer, and no error, because both are `number => number`. That's why the next section switches to unequal types.

Add in the following `trace` helper and show how we can trace a value at each step in the pipeline.

```ts
const trace =
  (label: string) =>
  <T>(value: T): T => {
    console.log(label, "::", value);
    return value;
  };
```

Question - how do we type this?

Answer to explain: `T` goes on the inner function, because the label tells TypeScript nothing about the value. With `T` on the outer function, `const logTrimmed = trace("trimmed")` becomes `(value: unknown) => unknown`, and every type after it in the pipeline becomes `unknown` (checked in TypeScript 5.9.3). This is the currying post's lesson in reverse: there, `transform` carried the types, so the generics went on the first call.

## Link the three types in the two-function version

```ts
const pipe2 =
  <A, B, C>(first: (value: A) => B, second: (value: B) => C) =>
  (value: A): C =>
    second(first(value));

const compose2 =
  <A, B, C>(second: (value: B) => C, first: (value: A) => B) =>
  (value: A): C =>
    second(first(value));
```

Explain A to B to C with the currying post's summary check. There, `maxLength(160)` counted and compared in one function. Split it into `length` (`string => number`) and `atMost(160)` (`number => boolean`), where `const atMost = (limit: number) => (count: number) => count <= limit`. `pipe2(length, atMost(160))` infers `(value: string) => boolean`: A is `string`, B is `number`, C is `boolean`. `compose2(atMost(160), length)` builds the same function with the arguments reversed.

Then swap them: `pipe2(atMost(160), length)` is rejected. The error lands on `atMost(160)` and says it isn't assignable to `(value: number) => string`, a type TypeScript guessed from `length`. One sentence on this keeps readers from looking for the bug in the wrong place. (The generic `singleton`/`box` experiment moved to the follow-up noted under variadic composition.)

## Name the data, or leave it out

Introduce point-free style once `pipe2` works. This section is moved from the curried functions draft. Define `trim` and `toLowerCase` as one-argument string functions first, and link to the curried functions post once it is published.

```ts
// names the data
const normalizeExplicit = (value: string) => toLowerCase(trim(value));

// point-free: never names it
const normalizePointFree = pipe2(trim, toLowerCase);
```

Point-free functions are functions that are "free" of the points (data) they operate on. They don't need the data at the time of creation. It's like a team of functions. They're ready to operate at the moment they get called into the game.

`normalizePointFree` is point-free with respect to the string: it does not explicitly name or forward that parameter. It still accepts a string when called. The inner callbacks name their own `value`, so the point-free description applies to the outer definition, not every function inside it.

These ideas describe different parts of the example. `pipe2` is curried-style: it takes its functions first and returns a function that waits for the value. Supplying only the functions is partial application. Defining `normalizePointFree` without an explicit string parameter is point-free style.

Confirm TypeScript still infers `(value: string) => string` for both versions. Point-free is where generic inference gets fragile, so the generic `singleton`/`box` experiment stays out of this post (see the follow-up note under variadic composition).

## Add one more transformation

Add `trim` in front, because the currying post's `fitsSummary` counted the spaces. `pipe2` only takes two functions, so a third means nesting: `pipe2(trim, pipe2(length, atMost(160)))` or `pipe2(pipe2(trim, length), atMost(160))`. Both infer `(value: string) => boolean` and return the same results (checked: `true` for `"  hi  "`, `false` for 161 characters). Point that out here; the next section explains why it always works.

Then swap `trim` and `length` for the mismatched link: `pipe2(length, pipe2(trim, atMost(160)))` is rejected, with errors on both `length` and the inner `trim`. The nesting is clunky on purpose: it's the reason to want a variadic `pipe`.

## Why we can trust the chain

The determinism payoff. One idea ties the post together: a pure function call can be replaced with its result, the same substitution we do in algebra. Walk `fitsSummary` through it:

```ts
fitsSummary("  hi  ");
// = atMost(160)(length(trim("  hi  ")))
// = atMost(160)(length("hi"))
// = atMost(160)(2)
// = true
```

Then show the two laws as engineering guarantees:

- **Associativity: safe refactoring.** The two nestings from the last section return the same results, so we can pull out a sub-pipeline and name it (`normalize = pipe2(trim, toLowerCase)`) without changing behavior. The validator factory post's `createValidator(normalize, ...rules)` depends on this.
- **Identity: `trace` is safe to add and remove.** `trace` returns its input, so adding or removing it doesn't change the result. It's the same `id` as in the functor post (link once that post is published). Say plainly that `trace` logs, so it isn't pure: it's the one side effect we allow because it never touches the value.

Close the section with: types check that each connection fits, and purity makes each step return the same answer every time. Match the promise in "The question" to this: "we can reason about it like algebra" holds up, while "mathematically provable" promises more than TypeScript checks (`any`, casts, and the `unknown` inside `pipe`'s body are trusted, not checked).
