In [Strongly Typed Function Composition](/posts/function-composition), we built `pipe2`, a typed `pipe` that connects exactly two functions. In this post, we'll answer the next question: how do we type `pipe` and `compose` that take a variable number of functions while having TypeScript check every connection between them?

## Extend to variadic composition

At runtime, `.reduce()` and `.reduceRight` can hand each function's result to the next, so we're going to use it to create versions of `pipe` and `compose` that allow us to combine multiple layers of logic encapsulated within functions.

{/* We can use both `.reduce()` and `.reduceRight()` (for `compose`) to build functions */}

Our goal is to find the best way to type this - a way that will allow us to still benefit from TypeScript's type system while also enjoying the joys of composition.

For our first pass, we'll type the input functions as an array.

<TsSandbox
  id="variadic-unsafe-pipe"
  title="An array of any functions"
  code={unsafePipe}

/>

This compiles, but it doesn't help us. Both pipelines get the same type, so TypeScript can't tell the working one from the broken one. An array type describes every function the same way, which means it can't remember that `trim` returns a `string` and `length` expects one. The connections are gone.

We can't swap `any` for the safer `unknown`, either. A `(value: unknown) => unknown` has to accept _anything_, so TypeScript rejects `trim`, which only accepts strings.

## Leaning on overloads

What we need is a separate type for every connection, just like `pipe2` had `A`, `B`, and `C`. TypeScript gives us a way to do that: **overloads**. We write out one call signature for each number of functions we want to support, and TypeScript picks the one that matches the call:

<TsSandbox
  id="variadic-typed-pipe"
  title="Type pipe with overloads"
  code={typedPipe}
  files={{ "functions.ts": functionsSource }}
/>

These four call signatures describe ways to call the same `pipe` function. Each one covers a different number of steps.

Each signature repeats the trick that made `pipe2` work. Take the three-function signature. When we call `pipe(trim, length, atMost(160))`, TypeScript matches each function to a parameter and fills in the letters:

- `ab` is `trim`, so `A` is `string` and `B` is `string`.
- `bc` is `length`, so `B` is `string` and `C` is `number`.
- `cd` is `atMost(160)`, so `C` is `number` and `D` is `boolean`.

The shared `B` and `C` check the connections.

The three-function overload tells TypeScript that we want to go from `A` to `D`. The function we get back is `(a: A) => D`, which here works out to `(a: string) => boolean`.

Callers see the signatures in `Pipe`. The implementation still uses `any` to run the steps, so the overloads are the part that checks the connections at the call site.

<TsSandbox
  id="variadic-trace-pipeline"
  title="Add a generic trace step"
  code={tracePipeline}
  files={{ "functions.ts": functionsSource, "pipe.ts": pipeSource }}
/>

No nesting, and TypeScript still infers `(a: string) => boolean`. It even handles our generic `trace` in the middle: `trace("trimmed")` receives a `string`, so it returns a `string`, and `length` gets exactly what it expects.

Adding `trace` selects the four-function overload, so we're now going from `A` to `E`. Here, `A`, `B`, and `C` are `string`, `D` is `number`, and `E` is `boolean`. There is another connection to check, while the input and return types are still `string` and `boolean`.

## Typing compose

`compose` gets the same treatment. Its signatures match `Pipe`'s, with the parameters listed in reverse. The rightmost function runs first.

<TsSandbox

/>

`compose` uses `.reduceRight()` to run the same steps as `pipe(trim, length, atMost(160))`.

The `trace` version has four steps, just like our `pipe` example. We can also swap `trim` and `length` to see `compose` reject an incompatible connection. Choose **Edit this code**, then put the functions back in the correct order to clear the error.

There is one important thing to call out: our overloads have a limit, they stop at four functions. Pass in five, and TypeScript tells us `Expected 1-4 arguments, but got 5.` For a longer pipeline, we can add more signatures, or we can nest `pipe` or `compose` calls. Function composition is associative, so how we group the functions doesn't change the result.
