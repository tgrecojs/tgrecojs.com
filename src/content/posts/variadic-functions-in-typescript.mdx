## Extending to variadic composition

At runtime, `.reduce()` and `.reduceRight()` can hand each function's result to the next, meaning that we can use both to create versions of `pipe` and `compose` that allow us to combine multiple layers of logic.

Our goal is to find a way to type this that lets us benefit from TypeScript's type system while also enjoying the fruits of composition.

For our first pass, we'll type the rest parameter `...fns` as an array of functions.

<TsSandbox
  id="variadic-unsafe-pipe"
  title="An array of any functions"
  code={unsafePipe}
  files={{ "functions.ts": functionsSource }}
/>

This compiles, but it doesn't help us much. Both pipelines get the same type, so TypeScript can't tell the working one from the broken one.

This is because `Array<(value: any) => any>` gives every function the same input and return types. It forgets that `trim` returns a `string` and `length` expects one. The connections we so badly want are gone.

We can't swap `any` for the safer `unknown` either. A `(value: unknown) => unknown` has to accept _anything_, so when TypeScript sees `trim`, which only accepts strings, it rejects it.

## Won't you help me cure this, `overloads`?

With `pipe2`, we used a separate type for every connection: `A`, `B`, and `C`. With `pipe` and `compose`, we can lean on TypeScript's **overloads** feature.

**Overloads** give us a vehicle for writing out one call signature for each number of functions we wish to support. Once that's wired up, TypeScript will automatically pick the signature that matches the call.

<TsSandbox
  id="variadic-typed-pipe"
  title="Type pipe with overloads"
  code={typedPipe}
  files={{ "functions.ts": functionsSource }}
/>

These four call signatures describe ways to call the same `pipe` function, with each one covering a different number of steps. If you inspect the signature, you'll see each one repeat the trick that made `pipe2` work.

Let's consider the three-function signature associated with `pipe(trim, length, atMost(160))`. TypeScript matches each function to a parameter and fills in the letters:

- `ab` is `trim`, so `A` is `string` and `B` is `string`.
- `bc` is `length`, so `B` is `string` and `C` is `number`.
- `cd` is `atMost(160)`, so `C` is `number` and `D` is `boolean`.

The shared `B` and `C` check the connections.

The three-function overload tells TypeScript that we want to go from `A` to `D`. The function we get back is `(a: A) => D`, which here works out to `(a: string) => boolean`.

The implementation still uses `any` to run the steps, but thanks to the overloads, we're leveraging TypeScript's abilities to check the connections at the call site.

### An exercise in progressive overloads

Our overloads have a limit. They stop at four functions. Pass in five, and TypeScript tells us `Expected 1-4 arguments, but got 5.`

For a longer pipeline, we can add more signatures or nest `pipe` or `compose` calls. Function composition is associative, so how we group the functions doesn't change the result.
