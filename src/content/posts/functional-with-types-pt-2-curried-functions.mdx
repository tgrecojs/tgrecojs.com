## The question

How do we preserve types when we choose a transformation now and provide its data later?

## tightly coupled params

The type annotations tell us that:

- the `transform` function operates on items of type `A` and produces items of type `B`.

- the return value of our function is an array of `B`s.

Here, `lengths` is the resulting `number[]`. Both arguments have already been supplied, so there is no second function to call.

While this is no doubt useful, we can level up `mapValues` by transforming it into a curried function. The relationship between the arguments and the generics tells the story. We can preserve that relationship even when we change how the function receives its arguments.

> Currying turns a function that accepts multiple parameters into a sequence of functions that have an arity of one.

To simplify that a bit: arity is the term for describing the number of arguments a function will receive. If we look at the codeblock below, we'll find functions for addition and multiplication. The version with the trailing underscore is the curried version.

```ts
const add = (x: number, y: number) => x + y;
const add_ = (x: number) => (y: number) => x + y;

const multiply = (x: number, y: number) => x * y;
const multiply_ = (x: number) => (y: number) => x * y;
```

By transforming `add` and `multiply` to their curried versions, we can fix values as their first argument, and then call them throughout our code.

```ts
const addTen = add_(10);
const doubleNumber = multiply_(2);

addTen(5); // 15
doubleNumber(5); // 10
```

Now, let's take this information back to our `mapValues` example. `mapValues`. has an arity of 2, and it needs both of these arguments in order to execute. Every invocation of it has to align with the `<A, B>` template its input is annotated with. In the next section, we'll learn how to preserve our type annotations while promoting code reuse.

## Abstracting shared logic

Taking a look back at our initial example, let's identity the areas where we can perform abstraction - the process of decoupling code from its inputs to make code more reusability. The process of abstraction is key part of functional programming as it enables developers to share code like crazy! You can define a function once, and apply it throughout your codebase as needed.

## An aside on nomenclature

Earlier in the post, we explicitly defined currying, and looked at examples. Before we wrap this up, let's quickly discuss a few more terms used to describe concepts that we've been putting to use throughout this post so that in future posts, I can use these terms without feeling as though I need to provide context into what they mean.

### I see your currying, and I raise you Partial Application, and Point-Free

Currying and partial application go hand-in-hand. Each time that we've fixed a transformer function as the first argument of `mapValues`, we've _partially applied_ that function. If we were to define `getLengths` to explicitly take both arguments at once, we would no longer being making use of partial application.

We could write a wrapper that explicitly names the array:

```ts
// no partial application
const getLengths = (values: readonly string[]) =>
  mapValues((value: string) => value.length)(values);
```

But that's not all! We've also transformed `getLengths` from being a **point-free** function as a result of passing in `values` at creation time.

Point-free functions are functions that are "free" of the points (data) they operate on. They don't need the data at the time of creation. It's like a team of functions. They're ready to operate at the moment they get called into the game.

## Configure a validation check

Say a post editor allows 60 characters in a title and 160 in a summary. Both fields need the same length check with a different limit. With `maxLength`, we can choose the limit when we set up the form and check the text when someone types into it.

<TsSandbox

  code={maxLength}
/>

`maxLength(60)` returns a `(value: string) => boolean`. The returned function remembers the limit, so we can call `fitsTitle` with new text each time the input changes. The same text can pass one field's check and fail the other's.

A boolean answers whether the text fits. If we want the form to explain a failure, we can give the check a message. The function and its message are enough to describe a reusable validation rule.
