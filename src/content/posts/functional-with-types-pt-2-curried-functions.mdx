## The question

How do we preserve types when we choose a transformation now and provide its data later?

## tightly coupled params

The code block below shows the `mapValues` function which takes in a `transform` as well as a `values` array. We see the generic `<A, B>` being used to express the relationship between the `transform` function and the `values` it operates on.

The type annotations tell us that:

- the `transform` function operates on items of type `A` and produces items of type `B`.
- `values` is a `readonly` array of `A`s.
- the return value of our function is an array of `B`s.

While this is no doubt useful, we can level up `mapValues` by transforming it into a curried function. The relationship between the arguments and the generic tell the story. We can preserve this exact structure even if we transform it from its current version, in which it takes both arguments at once, into it's _curried_ verion.

> a curried function is a function that returns a function with an arity of one.

To simplify that a bit: arity is the term for describing the number of arguments a function will receive. The `mapValues` function we just looked at has an arity of 2. It needs both arguments in order to function. Every invocation of it has to align with the `<A, B>` template its input is annotated with. If we promote this to a curried function however, we find ourselves in a much better position for promoting code reusability throughout our systems.

## Name the relationship between the two calls

```ts
const mapValues =
  <A, B>(transform: (value: A) => B) =>
  (values: readonly A[]): B[] =>
    values.map(transform);

const getLengths = mapValues((value: string) => value.length);
const multiplyBy10 = mapValues((value: number) => value * 10);
```

Walk through A, B, and the returned function before discussing reusable validators. Accepting a readonly input array does not make the returned array readonly or freeze anything at runtime.
