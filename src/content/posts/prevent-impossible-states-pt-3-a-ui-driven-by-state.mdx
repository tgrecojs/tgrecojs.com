## Introduction

In an attempt to flex my full-stack muscles, I have been spending time putting out content centered around using TypeScript to build deterministic software. Thus far, I've discussed using [discriminated unions](/posts/prevent-impossible-states-pt-1-union-types), and demonstrated [how to apply union types to create finite state machines](/posts/prevent-impossible-states-pt-2-state-transitions). In this post, we'll introduce the view layer into the mix.

To recap: our goal for using state machines is to ensure our application code is protected from invalid or "impossible" states. An example of an impossible state might be seeing a "sign in" button in an application that you're already logged in to. This causes confusion, and adds noise to user stories that we're obligated to make as frictionless as possible.


### Recapping `TimerState` and `TimerEvent`

I previously laid out the `TimerState` and `TimerEvent` types shown below.

```ts
type TimerState =
  | { status: 'idle' }
  | { status: 'running'; remainingSeconds: number }
  | { status: 'paused'; remainingSeconds: number }
  | { status: 'finished' };

type TimerEvent =
  | { type: 'start'; durationSeconds: number }
  | { type: 'pause' }
  | { type: 'resume' }
  | { type: 'tick' }
  | { type: 'reset' };
```

These are the `state` and `event` values that will be passed into the `transition` function.


```ts
type Transition = (state: TimerState, event: TimerEvent) => TimerState;

const transition: Transition = (state, event) => {
  if (event.type === 'reset') {
    return { status: 'idle' };
  }

  switch (state.status) {
    case 'idle':
      return event.type === 'start'
        ? { status: 'running', remainingSeconds: event.durationSeconds }
        : state;

    case 'running':
      switch (event.type) {
        case 'pause':
          return { status: 'paused', remainingSeconds: state.remainingSeconds };
        case 'tick':
          return state.remainingSeconds > 1
            ? { status: 'running', remainingSeconds: state.remainingSeconds - 1 }
            : { status: 'finished' };
        default:
          return state;
      }

    case 'paused':
      return event.type === 'resume'
        ? { status: 'running', remainingSeconds: state.remainingSeconds }
        : state;

    case 'finished':
      return state;

    default: {
      const unreachable: never = state;
      return unreachable;
    }
  }
};
```

With that recap finished, we can move forward with connecting this logic to our UI. While this example might seem fairly barebones, it still demonstrates an incredibly important practice of isolating business logic from the view logic to ensure our UI is fully deterministic.

## Defining our state map
Before we wire up our UI, let's sketch out how everything should function. The table below explicitly defines the "status -> control" relationship for each `state.status` option.

| Status | Controls |
| --- | --- |
| `idle` | Start |
| `running` | Pause, Reset |
| `paused` | Resume, Reset |
| `finished` | Reset |

When `state.status` is `idle`, our view will enforce that only the "Start" control is rendered. When `state.status` is `running`, our view will enforce that "Pause" and "Reset" controls are rendered. And so on.

### Catching a missing view

We can use the same [exhaustiveness check](https://www.typescriptlang.org/docs/handbook/2/narrowing.html#exhaustiveness-checking) we used in our transition function. Here's a shorter view that returns status text, with the `paused` case deliberately left out:

<TsSandbox id="timer-view-exhaustiveness" title="A missing paused view" code={timerViewExhaustiveness} files={{ 'timer.ts': timer }} />

At `const unreachable: never = state`, TypeScript reports:

```text
Type '{ status: "paused"; remainingSeconds: number; }' is not assignable to type 'never'.
```

We've handled the other three statuses, so `state` can still be a paused timer when it reaches `default`. Adding this case before `default` clears the error:

```ts
case 'paused':
  return `Paused: ${state.remainingSeconds} seconds remaining`;
```

This checks that we've handled every status. It doesn't check that we've included the right buttons inside each case. If we handle `paused` but forget its "Resume" button, that still type-checks.

## Sending events from the UI

Our transition function is our API for managing the timer's state. If someone clicks "Pause", we send a `pause` event and let the function determine the next state. We're keeping our business logic out of the view. The view can just take the values it needs to show the appropriate controls.

I've historically been very anti-`useEffect` (as per guidance from the [react.js core team](https://react.dev/learn/you-might-not-need-an-effect)). In production systems, I'll reach for a state management library, or something like [TanStack query](https://tanstack.com/query/latest/docs/framework/react/overview) to handle my async logic. Regardless of how it's done, the goal of keeping application logic separate from my view code remains the same. For this example, though, a small `useEffect` isolated in a custom hook fits will have to do.

## Isolating clock logic into a custom hook

Right now the timer shows its remaining time but never counts down, so it needs a clock. We keep that subscription in a [custom hook](https://react.dev/learn/reusing-logic-with-custom-hooks), separate from the view. 

<ReactSandbox id="timer-hook" title="useTimer.ts" file="useTimer.ts" code={useTimer} files={{ 'timer.ts': timer, 'TimerView.tsx': timerView, 'Timer.tsx': timerComponent, 'ControlButton.tsx': timerControlButton }} render="Timer" renderFrom="Timer.tsx" />

In `useTimer.ts`, `useReducer` manages the state, and `useEffect` sends a `tick` event every second while the status is `running`. With that in place, we can update `Timer` to call `useTimer()`. Our rendering logic still derives directly from state. It depends on `state.status` and `dispatch`, so updating `remainingSeconds` doesn't restart the interval.

## Adding more timers

We've contained the beast, so to speak. Before we wrap up, let's enjoy the fruits of our labor and see how quickly we can extend our code so that users can create multiple timer widgers, each with its only controls. 

Each `Timer` calls `useTimer`, so [each instance has its own state](https://react.dev/learn/preserving-and-resetting-state). Sending a "pause" or a "reset" event to one won't change the state of a second or third timer - each is totally independent, just as we intended.

## The lesson

We've successfully combined discriminated unions, finite state machines to create a fully deterministic user interface. The UI stays in sync with our state. 

The main benefits for me are that our UI stays in sync with our state. A paused timer gives the user the option to resume or reset it, and each timer is managed independently. We added the ability to create more timers without rewriting the rules for how a timer behaves.

The exhaustiveness check catches a missing state case. We still need to check that each view shows the right controls.
