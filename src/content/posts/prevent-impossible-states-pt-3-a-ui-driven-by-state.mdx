## Introduction

This post is going to cover using the data model introduced prior in the series. We're going to take a look at using our tagged unions 

In [Part 2](/posts/prevent-impossible-states-pt-2-state-transitions), we defined our timer's states and transitions. Now I want to use that same model to determine what the user sees.

When someone first opens our timer, they should only have the option to start it. They shouldn't be able to pause or reset a timer that hasn't started. We already have the timer's state, so let's use it to decide which controls to show.

## Connecting the timer to React

Our transition function already takes a state and an event and returns the next state. React's [useReducer](https://react.dev/reference/react/useReducer) lets us reuse that function: React holds the current state, and we send events using `dispatch`.

## Rendering the controls for each state

The `reset` event is valid in every state, but we don't need to offer a Reset button while the timer is already `idle`.

We can use a `TimerView` component to render the controls for each status:

| Status | Controls |
| --- | --- |
| `idle` | Start |
| `running` | Pause, Reset |
| `paused` | Resume, Reset |
| `finished` | Reset |

### Catching a missing view

What if we forget to handle the `paused` state? We can use the same [exhaustiveness check](https://www.typescriptlang.org/docs/handbook/2/narrowing.html#exhaustiveness-checking) we used in our transition function. Here's a shorter view that returns status text, with the `paused` case deliberately left out:

<TsSandbox id="timer-view-exhaustiveness" title="A missing paused view" code={timerViewExhaustiveness} files={{ 'timer.ts': timer }} />

At `const unreachable: never = state`, TypeScript reports:

```text
Type '{ status: "paused"; remainingSeconds: number; }' is not assignable to type 'never'.
```

We've handled the other three statuses, so `state` can still be a paused timer when it reaches `default`. Adding this case before `default` clears the error:

```ts
case 'paused':
  return `Paused: ${state.remainingSeconds} seconds remaining`;
```

Try adding it in the editor, then use **Reset code** to restore the missing-case example.

This checks that we've handled every status. It doesn't check that we've included the right buttons inside each case. If we handle `paused` but forget its Resume button, that still type-checks.

## Sending events from the UI

Our transition function is our API for managing the timer's state. If someone clicks Pause, we send a `pause` event and let the function determine the next state. We're keeping our business logic out of the view. The view can just take the values it needs to show the appropriate controls.

I've historically been very anti-`useEffect`. In production, I usually reach for a state management library, or avoid Effects altogether, to keep application logic separate from my view code. For this example, though, a small Effect isolated in a custom hook fits.

Right now the timer shows its remaining time but never counts down, so it needs a clock. We keep that subscription in a [custom hook](https://react.dev/learn/reusing-logic-with-custom-hooks), separate from the view. In `useTimer.ts`, `useReducer` manages the state, and `useEffect` sends a `tick` event every second while the status is `running`:

<ReactSandbox id="timer-hook" title="useTimer.ts" file="useTimer.ts" code={useTimer} files={{ 'timer.ts': timer, 'TimerView.tsx': timerView, 'Timer.tsx': timerComponent }} render="Timer" renderFrom="Timer.tsx" />

`Timer` now calls `useTimer()` where it called `useReducer` before. `TimerView` doesn't change. This Effect only [synchronizes with the browser clock](https://react.dev/learn/you-might-not-need-an-effect), so our rendering logic still derives directly from state. It depends on `state.status` and `dispatch`, so updating `remainingSeconds` doesn't restart the interval. Because it counts interval callbacks, it can drift from wall-clock time.

When a running timer has one second left, the next `tick` returns `{ status: 'finished' }`, which has no `remainingSeconds`, so the view offers only Reset.

The UI only offers actions appropriate to its current state, but other code can still send an event. If `pause` arrives while the timer is `idle`, our transition function intentionally leaves the state unchanged.

## Adding more timers

We only had to write one transition function. Now we can let users create multiple timer widgets, each with its own controls. Each `Timer` calls `useTimer`, so [each instance has its own state](https://react.dev/learn/preserving-and-resetting-state). Pausing or resetting one won't change the state of a second or third timer.

In `Timers.tsx`:

<ReactSandbox id="timers" title="Timers.tsx" file="Timers.tsx" code={timers} files={{ 'timer.ts': timer, 'TimerView.tsx': timerView, 'Timer.tsx': timerComponent, 'useTimer.ts': useTimer }} />

The parent keeps track of which timers exist. Each timer keeps track of its own status and remaining time. We create each ID when the user clicks the button and keep it as a [stable key](https://react.dev/learn/rendering-lists#keeping-list-items-in-order-with-key), so React can identify the existing timers when we add another one.

Try creating two timers, starting both, and pausing or resetting just one. The other timer should keep its state.

## The lesson

The main benefit for me is that our UI stays in sync with our state. A paused timer gives the user the option to resume or reset it, and each timer is managed independently. We added the ability to create more timers without rewriting the rules for how a timer behaves.

The exhaustiveness check catches a missing state case. We still need to check that each view shows the right controls.
