## Introduction

In an attempt to flex my full-stack muscles, I have been spending time putting out content centered around using TypeScript to build deterministic software. Thus far, I've discussed using [discriminated unions](/posts/prevent-impossible-states-pt-1-union-types), and demonstrated [how to apply union types to create finite state machines](/posts/prevent-impossible-states-pt-2-state-transitions). In this post, we'll bring the view layer into the mix.

To recap: our goal for using state machines is to ensure our application code is protected from invalid or "impossible" states. An example of an impossible state might be seeing a "sign in" button in an application that you're already logged in to. This causes confusion, and adds noise to user flows that we're obligated to make as frictionless as possible.


### Recapping `TimerState` and `TimerEvent`

I previously laid out the `TimerState` and `TimerEvent` types shown below.

```ts
type TimerState =
  | { status: 'idle' }
  | { status: 'running'; remainingSeconds: number }
  | { status: 'paused'; remainingSeconds: number }
  | { status: 'finished' };

type TimerEvent =
  | { type: 'start'; durationSeconds: number }
  | { type: 'pause' }
  | { type: 'resume' }
  | { type: 'tick' }
  | { type: 'reset' };
```

These are the `state` and `event` values that will be passed into the `transition` function.

```ts
type Transition = (state: TimerState, event: TimerEvent) => TimerState;
```

The full implementation is in [Pt. 2](/posts/prevent-impossible-states-pt-2-state-transitions#writing-the-transition-function), and in the `timer.ts` tab of each sandbox below.

With that, we can move forward with connecting this logic to our UI. While this example might seem fairly barebones, it still demonstrates an important practice of isolating business logic from the view logic to ensure our UI is deterministic.

## Defining our state map

Before we wire up our UI, let's sketch out how everything should function. The table below explicitly defines the "status → control" relationship for each `state.status` option.

| Status | Controls |
| --- | --- |
| `idle` | Start |
| `running` | Pause, Reset |
| `paused` | Resume, Reset |
| `finished` | Reset |

When `state.status` is `idle`, our view will enforce that only the "Start" control is rendered. When `state.status` is `running`, our view will enforce that "Pause" and "Reset" controls are rendered. And so on.

## Connecting the timer to React

The `transition` function is already in the correct shape to be passed into React's [useReducer](https://react.dev/reference/react/useReducer) API. In return, we'll get the `state`, which will give us the `status`, `remainingSeconds`, etc., and a `dispatch` function we'll use to send our `TimerEvent`s.

## Rendering the controls for each state

We know that each control needs to dispatch its corresponding event, so we can abstract that shared logic into a `ControlButton` component.

```tsx
import type { Dispatch } from 'react';
import type { TimerEvent } from './timer';

export type TimerControlProps = {
  event: TimerEvent;
  label: string;
  dispatch: Dispatch<TimerEvent>;
};

export const ControlButton = ({ event, label, dispatch }: TimerControlProps) => (
  <button type="button" onClick={() => dispatch(event)}>
    {label}
  </button>
);
```

`Dispatch<TimerEvent>` describes a function that accepts a `TimerEvent`. We'll wire our component up to invoke it `onClick`, so [dispatch runs when the user clicks](https://react.dev/learn/responding-to-events#adding-event-handlers). `TimerView` is what we'll use to determine which `ControlButton`s are rendered.

### Catching a missing view

What if we forget to handle the `paused` state? We can use the same [exhaustiveness check](https://www.typescriptlang.org/docs/handbook/2/narrowing.html#exhaustiveness-checking) we used in our transition function. Here's a shorter view that returns status text, with the `paused` case deliberately left out:

<TsSandbox id="timer-view-exhaustiveness" title="A missing paused view" code={timerViewExhaustiveness} files={{ 'timer.ts': timer }} />

At `const unreachable: never = state`, TypeScript reports:

```text
Type '{ status: "paused"; remainingSeconds: number; }' is not assignable to type 'never'.
```

We've handled the other three statuses, so `state` can still be a paused timer when it reaches `default`. Adding this case before `default` clears the error:

```ts
case 'paused':
  return `Paused: ${state.remainingSeconds} seconds remaining`;
```

This checks that we've handled every status. It doesn't check that we've included the right buttons inside each case. If we handle `paused` but forget its "Resume" button, that still type-checks.

## Isolating clock logic into a custom hook

Right now the timer shows its remaining time but never counts down, so it needs a clock.

I've historically been very anti-`useEffect` (as per guidance from the [React team](https://react.dev/learn/you-might-not-need-an-effect)). In production systems, I'll reach for a state management library, or something like [TanStack Query](https://tanstack.com/query/latest/docs/framework/react/overview) to handle my async logic. Regardless of how it's done, the goal of keeping application logic separate from my view code remains the same. For this example, though, a small `useEffect` isolated in a custom hook will have to do.

We keep that subscription in a [custom hook](https://react.dev/learn/reusing-logic-with-custom-hooks), separate from the view.

<ReactSandbox id="timer-hook" title="useTimer.ts" file="useTimer.ts" code={useTimer} files={{ 'timer.ts': timer, 'TimerView.tsx': timerView, 'Timer.tsx': timerComponent, 'ControlButton.tsx': timerControlButton }} render="Timer" renderFrom="Timer.tsx" />

In `useTimer.ts`, `useReducer` manages the state, and `useEffect` sends a `tick` event every second while the status is `running`. With that in place, we can update `Timer` to call `useTimer()`. This Effect only [synchronizes with the browser clock](https://react.dev/learn/you-might-not-need-an-effect), so our rendering logic still derives directly from state. It depends on `state.status` and `dispatch`, so updating `remainingSeconds` doesn't restart the interval.

Clicking the "Run" button in the sandbox below should display our finished `Timer`. Go on, give it a try.

<ReactSandbox id="timer-with-hook" title="Timer.tsx" file="Timer.tsx" code={timerComponent} files={{ 'timer.ts': timer, 'TimerView.tsx': timerView, 'useTimer.ts': useTimer, 'ControlButton.tsx': timerControlButton }} />

As expressed in our `transition` function, the next `tick` after `state.remainingSeconds` reaches `1` returns `{ status: 'finished' }`, causing the view to update so that only "Reset" is available.

## Adding more timers

We've contained the beast, so to speak. Before we wrap up, let's enjoy the fruits of our labor and see how quickly we can extend our code so that users can create multiple timer widgets, each with its own controls.

Each `Timer` calls `useTimer`, so [each instance has its own state](https://react.dev/learn/preserving-and-resetting-state). Sending a `pause` or a `reset` event to one won't change the state of a second or third timer - each is totally independent, just as we intended.

The parent keeps track of which timers exist. Each timer keeps track of its own status and remaining time. We create each ID when the user clicks the button and keep it as a [stable key](https://react.dev/learn/rendering-lists#keeping-list-items-in-order-with-key), so React can identify the existing timers when we add another one.

Try creating two timers, starting both, and pausing or resetting just one. The other timer should keep its state.

## What this does not solve yet

The exhaustiveness check makes sure every status has a view. It doesn't make sure each view is right. If the `paused` case drops its "Resume" button, everything still type-checks, and the user is stuck with a timer they can only reset. The table at the top of this post is our spec, and right now nothing checks the view against it. A component test for each status would close that gap.

## The lesson

In the intro, I used a "sign in" button on a page you're already logged in to as an example of an impossible state. That bug usually comes from the UI keeping its own copy of the truth: an `isLoggedIn` flag in one place, a `showSignIn` flag in another, and eventually they disagree.

Our timer's view doesn't keep a copy. It reads `state.status` and renders the controls for that status. Nothing else.

Each post in this series added one piece:

- [Pt. 1](/posts/prevent-impossible-states-pt-1-union-types): discriminated unions define the shapes our state can take.
- [Pt. 2](/posts/prevent-impossible-states-pt-2-state-transitions): the transition function defines which changes between those shapes are allowed.
- Pt. 3: the view renders only the actions the current state allows.

That gives us two layers of protection. The UI only offers valid actions, and if an invalid event gets sent anyway, like `pause` while the timer is `idle`, `transition` leaves the state alone. It's also why adding more timers only took one small component. The rules didn't change, so we didn't have to touch them.
