## Introduction

In [Part 2](/posts/prevent-impossible-states-pt-2-state-transitions), we defined our timer's states and transitions. Now let's use that same model to build a React UI.

When someone first opens the timer, it's idle. They should only see the option to start it. There isn't a running timer to pause or anything to reset. The controls we offer should follow the timer's current state.

## Connecting the timer to React

Our transition function already takes a state and an event and returns the next state. React's [useReducer](https://react.dev/reference/react/useReducer) lets us reuse that function: React holds the current state, and we send events using `dispatch`.

When someone clicks Start, we send a `start` event with `durationSeconds: 30`. Our transition function returns a state with `status: 'running'` and `remainingSeconds: 30`. React then renders the UI with that state.

Using the types and transition function from Part 2 in a module called `timer.ts`, we can connect our first button:

```tsx
import { useReducer } from 'react';
import { transition, type TimerState } from './timer';

const initialState: TimerState = { status: 'idle' };

const Timer = () => {
  const [state, dispatch] = useReducer(transition, initialState);

  return (
    <section>
      <p>Status: {state.status}</p>
      {state.status === 'idle' ? (
        <button
          onClick={() => dispatch({ type: 'start', durationSeconds: 30 })}
        >
          Start
        </button>
      ) : null}
    </section>
  );
};
```

For now, starting the timer changes the displayed status and removes the Start button. The transition rules still live in `transition`; the click handler only sends the event.

## Rendering the controls for each state

Now that the timer has started, we can give the user the option to pause or reset it. When it's paused, they can resume or reset it. Once it's finished, they can reset it to start again.

The `reset` event returns the timer to `idle`, discarding any remaining time. Our transition function accepts that event in every state, but we don't need to offer a Reset button while the timer is already idle.

We can use a `TimerView` component to render the controls for each status:

| Status | Controls |
| --- | --- |
| `idle` | Start |
| `running` | Pause, Reset |
| `paused` | Resume, Reset |
| `finished` | Reset |

### Catching a missing view

What if we forget to handle the paused state? We can use the same [exhaustiveness check](https://www.typescriptlang.org/docs/handbook/2/narrowing.html#exhaustiveness-checking) we used in our transition function. Here's a shorter view that returns status text, with the `paused` case deliberately left out:

At `const unreachable: never = state`, TypeScript reports:

```text
Type '{ status: "paused"; remainingSeconds: number; }' is not assignable to type 'never'.
```

We've handled the other three statuses, so `state` can still be a paused timer when it reaches `default`. Adding this case before `default` clears the error:

```ts
case 'paused':
  return `Paused: ${state.remainingSeconds} seconds remaining`;
```

This checks that we've handled every status. It doesn't check that we've included the right buttons inside each case. If we handle `paused` but forget its Resume button, that still type-checks.

### Rendering the buttons

The full component uses that same check. In `TimerView.tsx`:

```tsx
import type { Dispatch } from 'react';
import type { TimerEvent, TimerState } from './timer';

type TimerViewProps = {
  state: TimerState;
  dispatch: Dispatch<TimerEvent>;
};

export const TimerView = ({ state, dispatch }: TimerViewProps) => {
  switch (state.status) {
    case 'idle':
      return (
        <button onClick={() => dispatch({ type: 'start', durationSeconds: 30 })}>
          Start
        </button>
      );

    case 'running':
      return (
        <section>
          <p>Running: {state.remainingSeconds} seconds remaining</p>
          <button onClick={() => dispatch({ type: 'pause' })}>Pause</button>
          <button onClick={() => dispatch({ type: 'reset' })}>Reset</button>
        </section>
      );

    case 'paused':
      return (
        <section>
          <p>Paused: {state.remainingSeconds} seconds remaining</p>
          <button onClick={() => dispatch({ type: 'resume' })}>Resume</button>
          <button onClick={() => dispatch({ type: 'reset' })}>Reset</button>
        </section>
      );

    case 'finished':
      return (
        <section>
          <p>Timer finished</p>
          <button onClick={() => dispatch({ type: 'reset' })}>Reset</button>
        </section>
      );

    default: {
      const unreachable: never = state;
      return unreachable;
    }
  }
};
```

Our `Timer` component can now pass the current state and `dispatch` to that view. Replace its earlier implementation in `Timer.tsx` with:

```tsx
import { useReducer } from 'react';
import { transition, type TimerState } from './timer';
import { TimerView } from './TimerView';

const initialState: TimerState = { status: 'idle' };

export const Timer = () => {
  const [state, dispatch] = useReducer(transition, initialState);

  return <TimerView state={state} dispatch={dispatch} />;
};
```

We're using our state machine to deterministically render the UI: given the same timer state, this component renders the same controls. We don't need separate state variables to track whether Pause or Resume should appear. The `never` check also means that adding a new status without a matching view produces a type error.

## Sending events from the UI

Our transition function is our API for managing the timer's state. The button handlers send events to it, rather than deciding the next state themselves. This keeps our transition rules separate from our view logic: the view takes the resulting state and renders the appropriate controls.

If someone clicks Pause with 20 seconds remaining, we send a `pause` event. Our transition function returns a state with `status: 'paused'` and `remainingSeconds: 20`.

React renders the paused view, giving the user the option to resume or reset. We haven't changed the remaining time; we've changed the timer's status and, with it, the controls the user sees.

To advance the timer in this example, add a manual Tick button alongside Pause and Reset in the `running` case:

```tsx
<button onClick={() => dispatch({ type: 'tick' })}>Tick (advance one second)</button>
```

Each click sends one `tick` event. We're advancing the timer ourselves here; there's no clock running in the background.

When a running timer has one second left, the next tick returns `{ status: 'finished' }`. That state doesn't contain `remainingSeconds`. Our view displays "Timer finished" and offers Reset. Reset returns the timer to `idle`, where the user can start again.

The `case 'finished': return state` in our transition function handles events received after the timer has finished. It leaves the finished state unchanged. Reset still works because we handle that event before the status switch.

The UI only offers actions appropriate to its current state, but other code can still send an event. If `pause` arrives while the timer is idle, our transition function intentionally leaves the state unchanged.

## Adding more timers

We can take this a step further and let the user create multiple timer widgets. Each `Timer` calls `useReducer`, so [each instance has its own state](https://react.dev/learn/preserving-and-resetting-state). Pausing or resetting one timer doesn't change another timer's state.

In `Timers.tsx`:

```tsx
import { useState } from 'react';
import { Timer } from './Timer';

export const Timers = () => {
  const [timerIds, setTimerIds] = useState<string[]>([]);

  const createTimer = () => {
    const id = crypto.randomUUID();
    setTimerIds(ids => [...ids, id]);
  };

  return (
    <section>
      <button type="button" onClick={createTimer}>Create timer</button>
      <ul>
        {timerIds.map((id, index) => (
          <li key={id}>
            <h2>Timer {index + 1}</h2>
            <Timer />
          </li>
        ))}
      </ul>
    </section>
  );
};
```

The parent keeps track of which timers exist. Each timer keeps track of its own status and remaining time. We create each ID when the user clicks the button and keep it as a [stable key](https://react.dev/learn/rendering-lists#keeping-list-items-in-order-with-key), so React can identify the existing timers when we add another one.

Try creating two timers, starting both, and pausing or resetting just one. The other timer should keep its state. Both use the same transition function and view; we added list-management code without rewriting the timer rules.

## The lesson

Our UI stays in sync with our timer's state because that's what determines the controls we render. A paused timer offers Resume and Reset, and each timer widget manages its state independently.

We've kept the transition rules separate from the view and reused both to support multiple timers. The exhaustiveness check catches missing state cases; we still need to check that each view offers the controls we intended.
